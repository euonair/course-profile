EUonAIR AI-Ready Course Description Profile

Version 0.9 · namespace https://w3id.org/euonair/course# · vocabularies https://w3id.org/euonair/vocab/

The profile describes a course unit (module, course or module component) so that AI tools and course platforms can use its learning outcomes, level, workload, assessment and rules for AI use. It is the result of EUonAIR Milestone MS4, AI-Ready Course Descriptions (Work Package 4, Task 4.6), which derives the elements by triangulating standards and literature, partner practice and the needs of AI use.

The profile has a mandatory core of 18 elements, a recommended AI-readiness extension of 14 elements, an optional exchange and discovery extension of 32 elements and record metadata of 14 elements, five of them mandatory. Records are written in JSON-LD with schema.org/LRMI terms; elements specific to the profile use the euonair: namespace.

Conventions and AI-use policy rules

Normative conventions of the profile (Annex A.0 of the MS4 report):

  • Scope. This version applies to credit-bearing educational components (ECTS); non-credit provision is outside its scope.
  • Controlled values. Closed schemes (group mode, grading, generation method, review status, AI permission level, AI disclosure) accept only their listed values (§A.6, Annex C); the JSON Schema and the SHACL shapes check membership, not only the form of the IRI. Extensible schemes (activity type, assessment method, AI purpose) also accept other IRIs. Such custom values should carry a label, and consuming tools should warn when they meet one; this is a requirement for consumers that the validators of this release do not check. Ownership and versioning of the schemes are settled with the review of the profile (Section 10).
  • Validation scope. The rules of this annex fall into three groups. (1) *Implemented constraints*: cardinalities of the core and mandatory record fields, nested core requirements, closed value lists and the IRI form of references, checked by the JSON Schema and the SHACL shapes (Annex B.3, Annex I). (2) *Descriptive shapes*: SHACL field shapes of the extensions that name a field and its tier but contain no constraint; they never produce a validation result. (3) *Requirements for consumers and for a semantic validator*: sums, ranges and references (Annex B.3), labels and warnings for custom values, and the interpretation rules of Annex C. Passing both validators shows that a record meets the implemented constraints; it does not establish conformance with every rule of the profile.
  • Authoritative records. A record is authoritative for consumers only when it has been reviewed: its generation method is not AI-extracted without review (R09) and its review status is approved (R10). Otherwise it is a draft. A machine translation is never the authoritative version of a description (R14).
  • Missing values. A missing element means unknown; consumers do not infer it. A missing AI-use policy is never read as permission (Annex C.2).

Precedence rules for AI-use policies (Annex C.2): policy objects are used at course level (euonair:aiUsePolicy), at assessment level (euonair:aiCondition) and in offerings.

  1. For an assessment, the most specific applicable rule wins, in this order: assessment rule of the offering, assessment rule of the specification, course rule of the offering, course rule of the specification. The more specific scope (assessment) takes precedence over the more specific time (offering), so an assessment rule of the specification overrides a course rule of the offering. An offering that changes the rule for an assessment states it at assessment level of the offering.
  2. An overriding policy object replaces the object it overrides as a whole; attributes are not merged.
  3. A purpose listed as excluded is not allowed, even if it is also listed as permitted. A policy at level unrestricted takes no excluded purposes; a policy with exclusions uses permitted-with-disclosure.
  4. Purposes not listed fall back to the permission level (C.3).
  5. The rule valid for the learner's offering applies, not simply the most recently changed one.
  6. If no applicable, approved policy exists, the rule is unknown: tools must not assume permission and must refer students to the course rules.
  7. A course rule may be stricter than the institutional policy but should not be more permissive. Checking this is a governance task, not a schema rule.
